## A signed in screen that sometimes takes over 45 seconds

Second instance in two days, on screens no branch touched: `/portal/inquiries`
at 390 on 2026-10-11 (the 0068 board), `/portal/login` at 390 tonight (the 0073
board). Each recurred on no other board. The timeout was not raised.

**What is known.** mobile-overflow probes as a signed in administrator, so
`/portal/login` reads the session's profile and redirects to the dashboard,
which reads the database several times. In the same minute as tonight's
timeout, the audit processes logged Supabase connection aborts
(`ECONNABORTED`, `UND_ERR_SOCKET`) and the server logged
`[docs] file margins could not be read: TypeError: fetch failed`.

**The hypothesis, not yet confirmed by anything but that coincidence.** The
application's Supabase client (`src/lib/supabase.ts`) sets no fetch timeout, so
a socket that stalls holds a render for as long as the network does.
**Proposal for a ruling:** bound every application database request (for
example 20 seconds through the client's `fetch`), so a stall becomes an error
the page already handles; it changes how every read fails, which is why it is a
proposal rather than a fix tonight. Also open: the lock file showed
dispatch-scheduling's lock starting at 04:50:23Z, two minutes before this
board started at 04:52Z with the lock file absent; if the two ran together,
contention alone could explain it.
