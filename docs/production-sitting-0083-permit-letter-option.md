# Sitting: 0083, a permit letter records its option and schedule

Branch `feat/pl-determination`, built on `feat/design-addendum`, so it applies
after 0082. Written 2026-10-22. **Applied nowhere yet.** Development first,
then the board, then production in the same sitting as 0082 or after it.

## Why

Operator ruling of 2026-10-22 from the engineer's email
(`docs/rulings-2026-10-22.md`, section 1), for 254-PL-001: A is a pass with
no conditions; B is a pass with the condition listed in the letter's schedule,
and sealing is refused if the schedule is empty; C is repairs required.

A determination is written once, inside `eng_record_review_decision`, and never
changes, so the option and the schedule are recorded on it when it is written.
With the rule held by the row, a B with an empty schedule cannot be recorded,
so no sealing step can ever be handed one.

## What changes

| | |
| --- | --- |
| `eng_determinations.letter_option` | A, B or C, or null |
| `eng_determinations.letter_conditions` | the schedule, text[], default empty |
| check `eng_determinations_permit_letter_option_ck` | the ruling for 254-PL-001; both empty for every other protocol. Every comparison goes through `coalesce`, because a CHECK that evaluates to null passes |
| trigger `eng_determinations_conditions_are_written` | refuses a blank condition |
| `eng_record_review_decision` | 0068's function, byte for byte except the determination insert, which carries the two fields. Generated by `scripts/emit-pl-determination-migration.mjs` |

No drop statement. Every determination already recorded is a 254-RC-001 one
with neither field, so it satisfies the check.

## What this does not do

It does not open 254-PL-001 for ordering or seal any permit letter: that line
is not offered, and letter sealing is roof only until each line's letter is
built. It records the engineer's choice so that, when it is, the rule is
already in the record.
