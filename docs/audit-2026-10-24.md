### Stripe
Every call goes through the `stripe()` chokepoint in `src/lib/payments-stripe.ts`, which refuses a live key off production:

| Call | Purpose |
| --- | --- |
| `checkout.sessions.create` | order, batch or statement checkout, from server-computed lines, key `checkout:${orderId}` |
| `refunds.create` | refund, key `refund:${chargeRef}:${amount}` |
| `checkout.sessions.retrieve` | reconcile sweep |
| `webhooks.constructEvent` | webhook signature |
| `checkout.sessions.create` | partner subscription, key `partner-billing:${partnerId}` |
| `paymentIntents.retrieve`, `refunds.retrieve`, `checkout.sessions.retrieve` | account consistency check |

No call touches accounts, transfers, payouts, invoices, customers or subscriptions.

**The one webhook,** `POST /api/stripe/webhook`.
- **Signature:** checked on the raw body, and a bad one answers 400.
- **Events handled:** `checkout.session.completed` (order, batch, statement), `checkout.session.expired`, `charge.refunded`, `charge.refund.updated`, and the partner billing events. Anything else answers 200 and is logged.
- **Idempotency, order lane:** `eng_payment_events.event_id` is the primary key (0075). It is claimed in the same transaction as the money. Beneath it, a unique (provider, provider_ref) on `eng_order_payments`.
- **Idempotency, partner lane:** `eng_partner_billing_events.stripe_event_id`, deduplicated on 23505.
- **What it trusts:** amounts come from Stripe, and ids from metadata the server set. No browser-supplied amount is read.

**Agent's flags, to be confirmed in Phase 3:**
- S1. `startCheckout` and `startBatchCheckout` never ask the line gate. An order left awaiting payment before a protocol was voided can still be charged when checkout is reopened.
- S2. `/api/order-flow` opens a checkout for a duplicate draft, because placeOrder's idempotent return comes before the gate.
- S3. **Batch idempotency is global, not per account** (`ops-bulk.ts:116`, unique index in 0009). A second account sending the same `clientRequestId` would get back the first account's batch, and the bulk and v1 routes then open checkout on it, carrying the first account's addresses.
- S4. Job billing passes `"open"` to the gate whatever the mode.
- S5. `sendPaymentLink` is not idempotent. Each call makes a new order and a new Stripe link for the same file.
- S6. Partner checkout skips `chargesBlockedReason`.
- S7. `/portal/intake` shows prices without asking the line gate.
- S8. The batch decides coastal from the typed county while each order decides it from `resolveCounty`, so the charged batch share can differ from the order's own total. The trade price likewise lands on the batch share but not on the order snapshot.
- S9. A job-billing order stores only `total_cents`, so Stripe shows a single line with no named surcharge, against the rule stated at `payments-stripe.ts:56-61`.
- S10. Refunds on orders paid as part of a batch: the charge row is on the batch, so `settleDecision` and `cancelAndRefund` may find nothing to refund.
- S11. The refund idempotency key merges two genuine same-amount refunds on one charge within 24 hours.
- S12. `settleDecision` does not subtract pending refunds before refunding.
- S13. No refund door asks for a fresh code.
- S14. Partner billing webhook idempotency is not atomic: the event row is written before the state upsert, so if the upsert fails, the retry hits the duplicate key and the change is lost.
- S15. `eng_apply_order_paid` does not compare the paid amount with `total_cents`. The reconcile sweep does.
- S16. The fake payment provider accepts the literal signature `"fake-signature"` wherever `VERCEL_DEPLOYMENT_ID` is unset.
- S17. Review determinations ask for no fresh code, though a refusal queues a refund.
- S18. RC-001 approval asks for no fresh code, though it opens roof for sale.
- S19. Letter sealing never checks licence expiry.
- S20. `recordPartnerPayout` does not check that the statement belongs to the partner named in the URL, does not check its update's error, and writes the audit row regardless.
- S21. Phone intake with `paymentIntent: "invoiced"` raises no order. Whether anything bills it later could not be determined.
